# Repository guidance

- Always make each requested change in its own git worktree on a dedicated branch under the repository's ignored `.worktrees/` directory. Do not work directly in the repository root for branch or pull request work. After the change is complete and verified, commit it, push the branch, open a pull request, and enable auto-merge so it merges after the required tests pass. Wait for the pull request to pass and merge into `main`; then update the local `main` branch to the remote `main`, delete the task's git worktree, and only then move on to the next change. Multiple independent tasks may run in parallel only when the model judges that their branches, worktrees, and pull request lifecycles can remain safely isolated.
- Keep ordinary local builds side-effect-free: they may write only ignored build outputs or temporary files, never mutate tracked manifests, lockfiles, or source configuration. Make release version changes explicitly, commit them before packaging, and pass per-build provenance through generated ignored artifacts or environment variables.
- Expect to request or escalate permissions liberally whenever the workflow requires actions outside the current task worktree or sandboxed write area. This includes most git lifecycle operations, creating or deleting git worktrees, updating local `main`, writing git refs, interacting with GitHub through `gh`, launching the built app, or otherwise completing the required branch and PR lifecycle. Do not skip those steps just because they require approval.
- Conserve tokens when practical without making the work unnecessarily complex. When multiple approaches can accomplish an action, include token usage as one consideration when choosing between them. For long-running tasks, use appropriately long sleep or polling intervals instead of checking repeatedly at short intervals. A full GitHub build takes roughly 10-15 minutes, so sleep about five minutes between checks rather than polling every few seconds; a build that has only just started is never worth an immediate re-check.
- Take ownership of every build process you launch, and clean it up. Cargo fans out into many parallel `rustc` processes that together saturate the CPU, and they do not reliably die with the command that started them: interrupting, cancelling, or timing out a `cargo build`, `cargo check`, or `tauri build` regularly leaves orphaned `rustc` processes running indefinitely, which makes the whole machine unresponsive. So: prefer one build at a time; cap parallelism (for example `cargo build -j 4`) when a build runs alongside other work; after any interrupted or abandoned build, terminate the leftovers and confirm none remain with `pgrep -a -f 'rustc|cargo'`; and run that same check before starting a new build, so an earlier run's orphans are not still competing for the CPU. Never leave a build running when moving on to the next task.
- Do not stack pull requests. Branch every change off the default branch and target the pull request at it — never open a PR whose base is another feature branch. Auto-merge does not wait for checks on an unprotected base branch, so a stacked PR merges the instant it is mergeable and silently strands any commit pushed to the child afterwards. If a change genuinely depends on unmerged work, either wait for that work to land and branch off the updated default branch, or add both changes to the same pull request — a PR that carries more than one feature is fine.
- Keep unrelated or pre-existing worktree changes out of the commit.
- Use the $tdd skill / test-driven development whenever possible: add or update a failing test first, implement the smallest change that makes it pass, and then refactor while keeping the tests green.
- GitHub issues are the source of truth for outstanding work; there is no `TODO.md`. After completing each task, run `gh issue list` for new work, and close issues through the pull request that resolves them (`Closes #NN` in the PR body) rather than by hand. Use a fresh dedicated subagent for every new issue so it starts with a clean context. Assess each set of issues for safe parallel execution, but default to processing them sequentially when unsure — issues that touch the same component almost never parallelise safely, because their branches conflict.
- Use $diagnosing-bugs to help diagnose bugs
- Every user-facing feature must include a discoverable keyboard shortcut and automated coverage for that shortcut. Build its control with `ControlButton`, which declares `aria-keyshortcuts` and renders the matching visible hint from the same value, so the two cannot drift apart.
- After the pull request has merged, the local `main` branch has been updated from the remote `main`, and the task worktree has been deleted, build from that updated `main` for the platform you're on (`npm run build:linux` on Linux, `npm run build:mac` on macOS) and launch the freshly built app. That way, when the user returns to check things out, an up-to-date instance is already running for them to look at.
- If `gh` or GitHub network operations fail inside the sandbox, retry the same operation outside the sandbox with the required approval before treating GitHub as unavailable or marking the task blocked.
