# Repository guidance

- Always make each requested change in its own git worktree on a dedicated branch under the repository's ignored `.worktrees/` directory. Do not work directly in the repository root for branch or pull request work. After the change is complete and verified, commit it, push the branch, and open a pull request. Do not enable auto-merge and do not merge the pull request yourself: the user tests each feature manually and merges it. Once the required tests pass and the review steps below are done, tell the user the PR is ready and leave the worktree in place. After the user confirms the pull request has merged into `main`, update the local `main` branch to the remote `main`, delete the task's git worktree, and only then move on to the next change. Multiple independent tasks may run in parallel only when the model judges that their branches, worktrees, and pull request lifecycles can remain safely isolated.
- Review every pull request before handing it to the user. Once the PR is ready (verified and pushed) and before telling the user it is ready, run `/code-review high` on it and address the findings. Then run it again, up to 3 review rounds in total, addressing each round's findings and pushing the fixes. Stop early, without starting another round, as soon as a round's findings are all low-severity or show diminishing returns.
- CodeRabbit and GitHub Copilot are both enabled for this repository and may review a pull request automatically. If a CodeRabbit or Copilot review is in progress on the PR, wait for it to finish, then go through its findings. Respond to every finding, including duplicates and ones that are not relevant, and then resolve its thread. Fix each finding you judge valid and reasonable; use your own judgment about which those are. Like the `/code-review` rounds, this must be done before telling the user the PR is ready.
- Treat worktrees as temporary task directories: after a task is merged, remove its clean worktree before starting another task. At startup, inspect leftover worktrees and remove only those that are clean, completed or obsolete, and not in use by another task; keep their branches and commits unless branch deletion was explicitly requested. Never remove a dirty or active worktree without resolving ownership first.
- Keep ordinary local builds side-effect-free: they may write only ignored build outputs or temporary files, never mutate tracked manifests, lockfiles, or source configuration. Make release version changes explicitly, commit them before packaging, and pass per-build provenance through generated ignored artifacts or environment variables.
- Expect to request or escalate permissions liberally whenever the workflow requires actions outside the current task worktree or sandboxed write area. This includes most git lifecycle operations, creating or deleting git worktrees, updating local `main`, writing git refs, interacting with GitHub through `gh`, or otherwise completing the required branch and PR lifecycle. Do not skip those steps just because they require approval.
- Conserve tokens when practical without making the work unnecessarily complex. When multiple approaches can accomplish an action, include token usage as one consideration when choosing between them. For long-running tasks, use appropriately long sleep or polling intervals instead of checking repeatedly at short intervals. A full GitHub build takes roughly 10-15 minutes, so sleep about five minutes between checks rather than polling every few seconds; a build that has only just started is never worth an immediate re-check.
- Take ownership of every build process you launch, and clean it up. Cargo fans out into many parallel `rustc` processes that together saturate the CPU, and they do not reliably die with the command that started them: interrupting, cancelling, or timing out a `cargo build`, `cargo check`, or `tauri build` regularly leaves orphaned `rustc` processes running indefinitely, which makes the whole machine unresponsive. So: prefer one build at a time; cap parallelism (for example `cargo build -j 4`) when a build runs alongside other work; after any interrupted or abandoned build, terminate the leftovers and confirm none remain with `pgrep -a -f 'rustc|cargo'`; and run that same check before starting a new build, so an earlier run's orphans are not still competing for the CPU. Never leave a build running when moving on to the next task.
- Do not stack pull requests. Branch every change off the default branch and target the pull request at it — never open a PR whose base is another feature branch. A stacked PR is easily merged into its parent branch rather than `main`, which silently strands any commit pushed to the child afterwards. If a change genuinely depends on unmerged work, either wait for that work to land and branch off the updated default branch, or add both changes to the same pull request — a PR that carries more than one feature is fine.
- Keep unrelated or pre-existing worktree changes out of the commit.
- Use the $tdd skill / test-driven development whenever possible: add or update a failing test first, implement the smallest change that makes it pass, and then refactor while keeping the tests green.
- GitHub issues are the source of truth for outstanding work. After completing each task, run `gh issue list` for new work, and close issues through the pull request that resolves them (`Closes #NN` in the PR body) rather than by hand. Use a fresh dedicated subagent for every new issue so it starts with a clean context. Assess each set of issues for safe parallel execution, but default to processing them sequentially when unsure — issues that touch the same component almost never parallelise safely, because their branches conflict.
- When addressing an issue, post a comment on it before closing it through the pull request. Summarize what changed and include enough testing guidance for someone validating the result; call out any new keyboard shortcuts, UI, or behavior and how to exercise them. Keep the issue open until the pull request's `Closes #NN` automation closes it after merge.
- Use $diagnosing-bugs to help diagnose bugs
- Keep the concise help pane in sync with every user-facing feature: when a
  feature is added or changed, decide whether it warrants a help entry and
  update the pane and its shortcut coverage when it does.
- Every user-facing feature must include a discoverable keyboard shortcut and automated coverage for that shortcut. Build its control with `ControlButton`, which declares `aria-keyshortcuts` and renders the matching visible hint from the same value, so the two cannot drift apart.
- If `gh` or GitHub network operations fail inside the sandbox, retry the same operation outside the sandbox with the required approval before treating GitHub as unavailable or marking the task blocked.
- When setting up a new environment or diagnosing E2E test failures on Linux, ensure the following dependencies are installed to support `WebKitWebDriver` and headless integration tests: `sudo apt-get install -y webkitgtk-webdriver xvfb imagemagick gstreamer1.0-plugins-bad libgtk-3-0t64 libasound2t64 libatk-bridge2.0-0t64 libcups2t64` (note that older Ubuntu versions may use the non-`t64` package names).
- When addressing a code review finding - resopnd to the code review finding and resolve the comment thread. Even if you decide not to fix, still respond and resolve.
- Add the PR# to the session name if you're able to rename your own session.
- After you are done with your turns before going back to idle always display a link to the PR so the user could easily see which PR is being worked on and be able to click on it to view it on github.
